# 2.31 Lot 4 : notebook mis à jour, rejeu officiel, un défaut de l'API corrigé (2026-10-03)

**Pourquoi.** Les lots 1 à 3 et les arbitrages du 3 octobre avaient modifié le code et la
documentation, mais pas le notebook de certification, qui reste le livrable principal. Ce lot
l'aligne, puis le rejoue officiellement, avec MLflow tracé sur DagsHub.

**Notebook (v2.2).** 224 → 233 cellules ; modèles v2.1 inchangés.
- §0 et lecture : version v2.2, décisions D1–D16, hypothèses H01–H06.
- §1 résumé : système de décision révisé, limites mises à jour.
- §2.5 : D12, D14, D15 révisées, D16 ajoutée ; **§2.6 hypothèses de départ H01–H06** (H06 :
  échéance mensuelle, confirmée par le formateur, indice tiré de l'ancienneté).
- §4.1 et §7.11 : conservation du suivi sur 2 cycles, finalité « mesure d'impact ».
- **§9.4 calibration** : recalibration de Platt et isotonique comparées (Brier 0,1229 et 0,1238
  contre 0,1230) ; ECE 4,5 points sur le test, 1,3 hors pli : probabilités brutes conservées.
- §10.2 et §10.2.1 : filet de sécurité (135 comptes passés en Moyenne) ; le 10ᵉ compte du Top 10
  (CLV estimée 974 k€) est rattrapé et son explication le dit.
- **§12.4 recette D15** : critère d'origine conservé pour trace (Spearman 0,289), critère révisé
  (b') 82 % et (c') 91 % avec le filet, 80 % sans ; le filet couvre 8 des 14 faux négatifs critiques.
- **§13.2** : déclencheurs, procédure, et démonstration challenger contre modèle en service
  (ré-entraînement à l'identique : champion conservé ; gradient boosting : refusé).
- **§13.4** : protocole D12 révisé et **test à blanc (A/A)** sur le cycle de test : les trois
  écarts ont un intervalle qui contient zéro, mais l'écart B atteint 15 points sans aucune action,
  preuve qu'un seul cycle ne suffit pas ; rappel réel 82,5 % ; recette D15 recalculée par le
  rapprochement.
- §13.5 et **§13.6** : image GHCR et journal des décisions au versioning ; revue trimestrielle D16.
- §14 : tableau de bord, couverture du référentiel, recommandations ; §15 : vérifications
  (empreintes écrites, filet appliqué), inventaire de `src/`, glossaire.

**Exécution à blanc d'abord.** Le notebook a été exécuté une première fois hors pipeline (MLflow
local, sortie dans un dossier temporaire) pour vérifier chaque chiffre cité dans le texte avant le
rejeu officiel.

**Défaut de l'API trouvé et corrigé.** En vérifiant l'API avec le vrai modèle, une requête sans
aucune variable catégorielle (l'exemple du guide de démarrage) renvoyait une erreur 500 : la
colonne vide était de type numérique et l'encodeur one-hot la refusait. Défaut antérieur à ces
lots. La colonne est désormais gardée en type objet ; test ajouté (215 au total).

**Rejeu officiel.** `dvc repro -s certification` avec MLflow sur DagsHub, puis
`dvc repro -s cycles_simules`. Un premier rejeu (runs `cc17e1fe` et `c6d518e0`) a dû être refait
après la correction de l'API, dont le notebook dépend. **Runs de référence : churn
`e5a8174b04344cbe9eb349716c52be52`, CLV `1f47559922c14289be92043dd045ef03`.** Métriques
identiques (PR-AUC 0,7475, rappel 82,5 %, seuil 0,2832) ; modèle reproduit à l'identique (empreinte
`bf74f0389bb4`), désormais écrite dans `model_manifest.json` : `/ready` répond
`empreintes_verifiees: true`, et la porte de qualité de la CI vérifie ces empreintes.

**Non fait, assumé.** Le nom d'expérience MLflow par défaut de `src/tracking.py`, reporté du lot 0,
n'est pas modifié : aucun notebook ne l'utilise, et le changer imposerait de rejouer les notebooks
v1 (04 et 05), donc de réentraîner les modèles v1, pour un gain nul.

**Reste à faire.** Support de soutenance à refaire (l'actuel date de la v2.0) ; release GitHub à
publier (la page de garde pointe vers la v2.0) ; validations du DPO.
